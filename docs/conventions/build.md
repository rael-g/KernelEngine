# How does the build turn the tree into libraries, and where does everything land?

`zig build`, run at the repository root, is the only native entry point. The root `build.zig` builds
nothing itself: it fetches toolchains, runs vcpkg, and invokes every plugin's own `build.zig` as a
separate `zig build` (`build.zig:8`; `Ctx.plugin`, `build.zig:866-894`).

## Where output goes

Everything a build fetches or produces is under `build/` (`build.zig:15-16`, `36`):

| directory | holds |
|---|---|
| `build/tools/` | fetched toolchains: vcpkg, `slangc`, wgpu-native |
| `build/vcpkg-installed/<triplet>/` | the ports vcpkg installed |
| `build/zig-cache/` | one Zig cache for the root build and every plugin build |
| `<--prefix>/lib`, `/bin`, `/gen` | plugin libraries, executables, generated shader output |

`--prefix` is the install root the caller picks; every plugin is given the same one, so all plugin
libraries converge in one `lib/` (`build.zig:861-864`). `Ctx.cache_dir` is the fixed
`build/zig-cache` path passed to every sub-build as `--cache-dir` (`build.zig:16`, `85`, `869`),
whatever `--cache-dir` the caller gave the root.

## What a plugin receives

A plugin's `build.zig` runs standalone and takes its dependencies as `-D` options, never by reading
its neighbours: one include directory per domain it consumes, plus library paths
(`argF(b, "ke-asset-include", …)`, `build.zig:480-493`; `src/zig/window/glfw/build.zig:8-14`). The
root decides what each plugin can see, and a plugin that was not handed a domain cannot include it.

`Ctx.plugin` also passes `--release=off` or `--release=fast` from the root's optimize mode
(`build.zig:86`) and `-Dtarget=x86_64-windows-gnu` when the root target is Windows
(`build.zig:88`); on every other OS no target is passed and the plugin builds for the host.

## Tests

`Ctx.plugin` takes a required `Tests` argument, `.has_tests` or `.no_tests` (`build.zig:759`), so a
plugin cannot be declared without answering the question. A `.has_tests` plugin gets a second
`zig build test` invocation, given the same `-D` options as its library build, hung off the root's
`test` step (`build.zig:881-895`).

## Fetched tools

| tool | pinned at | fetched by |
|---|---|---|
| vcpkg | `2026-07-13` (`build.zig:18`) | `sh -c 'curl … && tar …'` (`build.zig:28-35`) |
| slangc | `2025.17.2` (`build.zig:64`) | `sh -c 'curl … && unzip …'` (`build.zig:73-78`) |
| wgpu-native | `v24.0.3.1` (`build.zig:244`) | `sh -c …` (`build.zig:257-263`) |

vcpkg runs in manifest mode against `vcpkg.json` with the overlay triplets in `vcpkg-triplets/`,
installing into `build/vcpkg-installed` (`build.zig:37-48`). The triplet is chosen by OS alone:
`x64-windows-zig` or `x64-linux-zig` (`build.zig:10-13`).

## Shaders

Each shader is compiled to WGSL by running `dotnet run scripts/compile_slang.cs` with the fetched
`slangc` (`build.zig:784-804`). An authored material is compiled once per pass: a wrapper that
binds the material into the pass's entry points is generated by
`dotnet run scripts/generate_material_wrapper.cs`, then compiled like any other shader
(`build.zig:844`). **The native build therefore needs the .NET SDK on the path**, not only Zig.
