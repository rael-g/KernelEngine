# 17 — Scene & Node Serialization

> **Status**: 📋 Architectural decision. Not implemented. This chapter freezes the model by which scene files (`*.scene.toml`, defined in chapter 15) map to live `Node` trees at runtime — the rules for what gets serialized, how types are resolved, and how the runtime hydrator stays portable across reflection-friendly and AOT-only build targets.

## 1. The model in one paragraph

A scene is a flat list of nodes. Each node declares a **fully qualified type name**, an optional **parent** reference (by `name`), a **transform**, and a **properties** table. The runtime resolves the type via a build-time-generated **class database**, instantiates the node, and hydrates its public properties from the TOML data. Built-in node types (`Camera`, `MeshRenderer`, `DirectionalLight`, …) live under the `KernelEngine.Framework` namespace and may be referenced by their short name; user types must use their full namespace-qualified name. The root of a scene is a plain `Node` by default — it does not need behavior.

## 2. Format recap

Full schema is documented in [15 - Serialization & Project Files §5](15%20-%20Serialization%20%26%20Project%20Files.md#5-scene-file-schema-scenetoml). Brief reminder of the shape:

```toml
[scene]
name    = "Level1"
version = 1

[[node]]
name = "Level1"
type = "Node"                       # plain organizational root

[[node]]
name = "Enemies"
type = "Node"
parent = "Level1"

[[node]]
name = "Boss"
type = "MyGame.Boss"                # user subclass — fully qualified
parent = "Enemies"
transform = { position = [10, 0, 5] }
properties = { Hp = 250, DisplayName = "First Boss" }

[[node]]
name = "MainCam"
type = "Camera"                     # built-in → implicit KernelEngine.Framework namespace
parent = "Level1"
properties = { Fov = 75 }
```

## 3. The two halves: discovery and hydration

Loading a scene is two distinct problems. Conflating them is the trap most engines fall into.

**Discovery** — given `type = "MyGame.Boss"`, find the runtime type. Done badly: scan every loaded assembly at runtime looking for matches. AOT-hostile, slow, fragile. Done well: a build-time **class database** maps every known type name to a constructor and a property setter table.

**Hydration** — given a constructed `Boss` instance and `{ Hp = 250 }`, set `boss.Hp = 250`. Done badly: `PropertyInfo.SetValue` per property at runtime — reflection in the hot path. Done well: source-generated setters per type, dictionary lookup, zero reflection.

The chapters that follow are about getting both halves right while keeping the door open for alternative implementations.

## 4. The class database — schema as data, not code

A build-time artifact (`class_database.toml`, generated under `build/native/` or similar) enumerates every Node-derived type the project ships with, and every property of each. It exists because:

- Tooling that is not the C# runtime needs to introspect node types (CLI editor, GUI editor, AI agent suggesting valid properties, future non-C# framework implementation).
- Coupling the schema to C# reflection makes it inaccessible to everything else and unsafe for AOT.
- Generating it at build time means no runtime scanning — fast cold-start, AOT-safe, deterministic.

Shape:

```toml
[[type]]
name      = "MeshRenderer"
namespace = "KernelEngine.Framework"
extends   = "Node"
abstract  = false

  [[type.property]]
  name    = "MeshHandle"
  kind    = "MeshHandle"           # primitive name or other type name in the DB
  default = 0
  hidden  = false                   # respects [HideInScene]

  [[type.property]]
  name    = "MaterialHandle"
  kind    = "MaterialHandle"
  default = 0
  hidden  = false

[[type]]
name      = "MyGame.Boss"
extends   = "Node"

  [[type.property]]
  name    = "Hp"
  kind    = "float"
  default = 100.0
```

The database is generated by a tool that walks user code — initially via C# reflection at build time (a `dotnet` source generator or a separate `ke gen class-db` command), eventually pluggable to walk other languages too. Whatever generates it, the output format is the contract.

## 5. Type resolution rules

- **Short name** (`type = "Camera"`) → assumed to live in `KernelEngine.Framework`. Convention only; if a user wants to put a class literally named `Camera` somewhere else, they must use the full name and the loader will warn on the collision.
- **Qualified name** (`type = "MyGame.Boss"`) → looked up directly in the class database.
- **Missing from DB** → fail loud at scene load with the offending type name and the file that referenced it. Never silently substitute `Node`.

## 6. Property serialization model — opt-out

Every `public { get; set; }` (or `init`-only) property of a node's runtime type is serialized by default. Two attributes govern the exceptions:

- `[HideInScene]` — opt a public property *out*. Default for properties the engine considers internal (`World`, `Entity`, `_componentId` — these are not public anyway, but the attribute is the recourse if a future refactor makes one public for legitimate reasons).
- `[ExposeInScene]` — opt a non-public property *in*. Rare; mainly for read-only-from-outside properties the editor still wants to show. Use sparingly.

**Inherited properties are included.** A `Boss : Node` instance serializes the union of `Boss`'s and `Node`'s public properties, minus hidden ones. Transform lives on `Node` and is therefore inherited by every subclass.

### 6.1 Supported property types

Round-tripped natively (no extra config):

- Primitives: `int`, `uint`, `long`, `float`, `double`, `bool`, `string`, enums.
- Vector types: `Vector2`, `Vector3`, `Vector4`, `Quaternion`.
- Handles: `MeshHandle`, `MaterialHandle`, `TextureHandle`, `ShadowMapHandle`.
- `Color` (when introduced — TOML array `[r, g, b, a]`).
- Resource references: `Mesh`, `Material`, `Texture` → serialized as `"res://path/to.resource.toml"`.
- Arrays / `List<T>` / `Dictionary<string, T>` of any of the above.

Unsupported (loader error at scene load):

- Generic types beyond the whitelisted collections.
- Delegates / function pointers / `Action`s (see §8).
- Object references that are not Resource refs or Node refs.

User types can opt into custom serialization by implementing `IBinarySerializable<T>` (a small interface with `Serialize(TomlWriter)` and `Deserialize(TomlReader)`). Avoid this unless really needed — the more custom serializers, the harder cross-language tooling becomes.

## 7. Subclasses, not attached scripts

In Godot, a Node and its Script are separate entities; you attach a `.gd` (or C# class) to a generic Node and the engine wires the behavior at runtime. **We reject this model.**

In KernelEngine, **the subclass IS the behavior.** A `class Boss : Node` is one type. You instantiate `Boss`, not `Node + attached script`. The scene's `type = "MyGame.Boss"` field plays the role Godot's script-path field plays — without the indirection.

Consequences:

- No `ScriptComponent` indirection at the framework level. (The C kernel's `ke_script_component` still exists for non-managed clients but Framework nodes do not use it — see chapter 6 and the Tier 2 Slice 5 commit.)
- Refactoring is a `git mv` + namespace adjustment. The scene's FQN tracks it via a refactor tool (`ke refactor rename-type old new --update-scenes`), not via path tracking.
- Behavior added at runtime via Action hooks (`node.OnUpdate = dt => ...`) is **not serializable** by design. Lambdas are code, not data; persisting them would require source serialization or weird IL stunts. If a behavior needs to live in a scene, it lives in a named subclass.

## 8. The hydrator interface — keep the implementation swappable

The runtime mechanism that turns "type name + property dict" into a live node sits behind an interface, not a reflection call:

```csharp
public interface INodeHydrator
{
    Node Create(string typeName, IDictionary<string, object> properties);
}
```

Three implementations, ordered by maturity and target:

| Impl | Use case | How it works |
|---|---|---|
| `ReflectionHydrator`   | Desktop dev builds | `Type.GetType` + `Activator.CreateInstance` + `PropertyInfo.SetValue`. Easy to implement, easy to debug, slow + AOT-hostile. |
| `SourceGenHydrator`    | AOT / mobile / shipping | Reads a generated registry: `Dictionary<string, Func<Node>>` + per-type setter tables. Zero reflection. Source generator emits the registry at compile time from `[NodeType]`-marked classes. |
| `DescriptorHydrator`   | Emergency / alt-language | Reads `class_database.toml` at runtime; uses a small dispatch table mapping type names to constructors registered manually. Last-resort fallback. |

Game code never instantiates a `Hydrator` directly — DI registers one based on the build configuration. Default in our codebase will be `ReflectionHydrator` until source gen exists; AOT/mobile targets force `SourceGenHydrator`.

## 9. AOT and mobile considerations

Specific things to watch:

- **No `Assembly.GetTypes()`** in the runtime path. Type discovery uses the class database, period.
- **No `Type.GetType(string)` in `SourceGenHydrator`.** The generated registry is the only entry point.
- **Trim safety** on `ReflectionHydrator`: every Node-derived type used in a scene must be marked `[DynamicallyAccessedMembers(...)]` or globally preserved via a trim descriptor. The source generator path sidesteps this entirely.
- **POCO serializable types** stay simple: no exotic generics, no interfaces-as-properties, no covariance tricks. The simpler the types, the more reliably the source generator handles them and the easier any other-language implementation has it.
- **No `DateTime.Now`** or other ambient state inside property defaults — defaults must be expressible in TOML.

## 10. Reverse direction — serializing a live tree to TOML

Saving (CLI `ke scene save`, editor "Save Scene") walks the Tree in pre-order, emits one `[[node]]` per node, and writes the property table from the same machinery that hydrates them — same supported types, same exclusion rules. The output is canonical (sorted keys within a table, two-space indent) so git diffs are minimal.

Equality round-trip is a requirement: `save(load(file)) == file` for any well-formed scene file.

## 11. Scene composition (sub-scenes)

A scene can include another scene as a subtree via the `include` field on a node, replacing `type`:

```toml
[[node]]
name = "EnemyA"
include = "res://scenes/EnemyTemplate.scene.toml"
transform = { position = [10, 0, 0] }
properties = { Hp = 50 }     # overrides on the included root
```

Mechanics:

- The included scene's nodes are grafted in. The named outer node here *is* the included scene's root.
- `properties` here override the included root's properties shallowly.
- Per-child overrides of the included subtree are out of scope for v1 — change the inner scene if you need them.

This is the disk equivalent of `Scene.Instantiate(tree, parent)` in code, and the format support for the reusable-bundle pattern introduced in Tier 2 Slice 2.

## 12. What is intentionally not specified

- **Binary scene format**. A compiled `.scene.bin` for shipping (faster cold start, no parser at runtime) is a future possibility, not v1.
- **Per-child overrides on `include`**. Deferred — composition stays shallow until a real use case appears.
- **Scene-level scripts** (something attached to "the scene" itself, not to a node). Use a root subclass if you need this: `type = "MyGame.LevelController"`. Avoids inventing a new concept.
- **Network replication metadata** on properties (e.g. `[Replicated]`). Multiplayer story is a separate chapter when it arrives.
